# SAT resolution oracle — feasibility and verification audit

Workspace `~/scratch/sat-resolution-oracle-audit-2026-10-26/`. No existing
repository or manuscript was modified; nothing was committed, pushed or published.
Source provenance, hashes and commands are in `MANIFEST.md`; the reduction and its
proof are in `ENCODING.md`; claims by evidence level are in `CLAIMS.md`; the pilot
parameters were fixed in `PILOT_PROTOCOL.md` before any pilot instance was run.

---

## 1. What this is

The V2 paper measures a solver's observational geometry through the resolution
diagnostic `ε̂(A,I) = max_{x∈S_I} min_{a∈A} d_H(x,a)`, and computes it by
enumerating `S_I` exhaustively. That caps the study at `n ≤ 20` — the paper says so
itself: the experiments are on random 3-SAT "with `n ≤ 20` (the ceiling imposed by
exhaustive ground-truth enumeration)".

This audit replaces the enumeration with `O(log n)` SAT queries, verifies that the
replacement is exact on the paper's own data, and measures what it costs.

**Headline: the oracle is exact on all 349 published instances, every result
carries an independently verified certificate, and it is already faster than
enumeration at `n = 18` and `n = 20`.** The decision cost is small; what is
expensive is the cardinality encoding's size and, in this implementation, proof
checking.

---

## 2. The reduction

For an integer radius `r`,

```
Q_r(x) = I(x) ∧ ⋀_{a∈A} [ d_H(x,a) ≥ r+1 ] ,
```

and `Q_r` is satisfiable exactly when `ε̂(A,I) > r`, so
`ε̂ = min{ r : Q_r unsatisfiable }`. Both directions are proved in `ENCODING.md` §2,
together with monotonicity in `r`, which is what licenses binary search. The
distance to each observed assignment is a cardinality constraint over the
**original `n` variables only**, because `d_H(x,a) = Σ_i lit(i,a)` with
`lit(i,a) = x_i` when `a_i = 0` and `¬x_i` when `a_i = 1`.

**This reduction is standard** — a farthest-solution query answered by bisection,
the same shape as textbook MaxSAT-by-bisection and solution-diversity encodings.
No novelty is claimed for it. What is new here is a verified implementation with a
certificate discipline, and the cost measurements below.

Edge cases are handled explicitly rather than by accident: `r = 0` becomes the
single clause `x ≠ a` with no auxiliary variables; `r ≥ n` is unsatisfiable **by
arithmetic**, returned without building a formula or calling a solver; an empty `A`
is the paper's categorical failure with `ε̂` undefined (not `0`, not `n`); an
unsatisfiable `I` with a nonempty `A` is refused rather than measured; and a
solver interrupt returns `UNKNOWN`, **never** UNSAT, after which the oracle reports
the interval it actually established. `A` is deduplicated and SHA-256-hashed before
the first query, and witnesses found by the oracle are never added to `A` — that
would change the object being measured.

## 3. Source audit, and one gap worth naming

Every detail of the paper's reported setup was checked against the sources, not
taken on trust: random 3-SAT, `n ∈ {16,18,20}`, densities `2.5/3.5/4.2`, WalkSAT
and Glucose3, and exactly **349** paired instances with nonempty observed sets
(`part10_results.json → per_instance_summary` has 349 rows out of 360 test
instances). All confirmed. `ε̂` is defined in `run_stage_b.py:85` exactly as in the
brief.

**The gap: the observed sets `A(I)` are not stored anywhere in the repository.**
The instance files deliberately contain only CNF clauses, and the result files
contain only derived summaries. A grep for assignment vectors across `data/`
returns nothing.

**It did not force a fresh reproduction.** Stage A is deterministic —
`rng = np.random.default_rng(STAGE_A_SEED + rec["id"])` per instance — so `A(I)` is
exactly regenerable, and it was regenerated by importing the repository's own
WalkSAT unchanged. The regeneration reproduces the published `A_I_size`,
`S_I_size` and `eps_hat`. **So this is a reproduction of the published experiment,
not merely of its design.** The one dependency is NumPy's PCG64 stream, which is
confirmed stable in practice: the published values reproduce under NumPy 2.5.4
although the paper pinned 1.26.4. `python-sat` is the paper's exact pin, `1.9.dev15`.

The regenerated observed sets also reproduce the published `A_I_size` and
`S_I_size` on all 349. Queries per instance: 4–5 (median 5), consistent with
`O(log n)` bisection. `ε̂` ranges over `0..5` on this ensemble. Machine-readable
table: `data/validate_all349.csv`.

**Encoding independence.** All four documented cardinality encodings available in
`python-sat` (`seqcounter`, `totalizer`, `sortnetwrk`, `mtotalizer`) return the
same radius on six cross-checked instances spanning all three sizes
(`results/cross_encoding.txt`).

**Controls: 31/31 pass** (`results/controls.txt`), covering every case the brief
asked for — singleton solution space, `A = S_I`, the full cube with `A = {0^n}`
(radius `n`) and `A = {0^n,1^n}` (radius `⌊n/2⌋`), an observed set missing a distant
isolated solution (where the returned witness *is* the unobserved solution),
duplicate assignments, empty `A`, unsatisfiable input, an off-by-one radius check,
and an auxiliary-variable collision.

**Two deliberately incorrect encoders are rejected by the independent checks.**
An encoder that never advances `top_id`, so distance constraints share auxiliary
variables, returns `ε̂ = 1` where the truth is `5`, and the exhaustive check refutes
it with a printed counterexample. An encoder using `d_H ≥ r` instead of `≥ r+1` is
caught even earlier, by the independent witness verifier: *"witness is at distance
4 < 5 from an observed assignment"*. Note that `verify.py` imports neither the
encoder nor any SAT library, so it cannot reproduce an encoder bug.

**A control-design finding worth recording.** The off-by-one encoder is *masked* on
instances with `ε̂ = n`, because the search is clamped at `r = n`; my first version
of that control used such an instance and passed a broken encoder. A discriminating
control must use `ε̂ < n`. This is in `CLAIMS.md` as C10 because it nearly produced
a false pass.

## 5. Certificate levels, and what actually holds

Three levels are tracked and reported separately for every instance:

1. **Witness-verified lower bound** — `Q_{k−1}` SAT with the model re-checked by
   `src/verify.py` (plain Boolean clause evaluation and direct Hamming distances).
2. **Solver-reported UNSAT upper bound** — `Q_k` UNSAT on the solver's word.
3. **Independently checked upper bound** — either a DRUP proof verified by
   `src/drup.py` against the standalone CNF of `Q_k` (all original clauses plus all
   cardinality clauses, no assumptions), or, for `n ≤ 24`, exhaustive enumeration,
   which uses neither a solver nor the encoder.

"Certified exact resolution" is used only when level 3 holds for the upper bound
and level 1 for the lower bound.

**A tooling limitation, stated plainly.** `drat-trim` was not used: fetching and
compiling third-party C source was declined by this environment, and no DRAT/LRAT
checker was installed. I wrote `src/drup.py` instead — a self-contained forward
RUP checker that imports no SAT library and shares no code with the encoder. It
rejects a tampered proof, and it agrees with the exhaustive route on every instance
where both ran. **But it has not been cross-validated against an established
checker, and that is a real gap** (`CLAIMS.md` N7). Where both routes exist the
exhaustive one is the stronger evidence, and at `n ≤ 20` it is available for every
instance — so the validation does not rest on my checker alone.

Deletion lines are ignored by the checker, which is sound: skipping deletions only
enlarges the accumulated clause set, every accumulated clause is inductively implied
by the input, and a propagation conflict under a superset of implied clauses still
witnesses implication by the input.

## 6. Paired comparisons, and the coverage denominator

The brief asks three protocols to be kept apart, and they are:

* **the paper's own protocol** — WalkSAT `K = 150, max_flips = 3000, p_noise = 0.5`;
  Glucose3 with `R = 5` permuted/phase-randomised `enum_models` runs truncated at
  `T = 8`;
* **a new fixed-budget comparison** — the same budgets applied at pilot sizes,
  labelled as new, with the budget *not* scaled with `n`;
* **a new comparison at equal numbers of distinct observed solutions** — the larger
  observed set truncated to the size of the smaller, in first-discovery order.

The third needs an explicit word, because it is easy to overclaim. Coverage is
`|A|/|S_I|`. On a **fixed** formula `|S_I|` is one and the same constant in both
ratios, so `|A_W| = |A_C|` forces `|A_W|/|S_I| = |A_C|/|S_I|` — the two coverage
fractions are **equal identically**, whatever `|S_I|` happens to be, and the
comparison therefore requires no knowledge of it. What cannot be said is what that
common coverage *is*: without the denominator there is no numerical coverage value,
and none is reported. The equality also holds only within a formula — across
formulas, equal `|A|` says nothing about equal coverage, because `|S_I|` differs.

## 7. Cost, and where it breaks

The measured picture is clear and it is not flattering to the oracle at small `n`.

| observation | measurement |
|---|---|
| `Q_r` is a 3-CNF (widths 2 and 3 from the sequential counter) — but over `n + n_aux` variables | instance 40 at `r = 3`: `n = 16`, **5 344 total variables**, 9 808 clauses |
| auxiliary variables scale as `n_aux ≈ 0.75 · \|A\| · n · (r+1)` | measured across `r = 1..5` |
| the distance constraints dominate the encoded problem completely | the original formula is `26.5 %` of clauses at `r = 0`, `0.41 %` at `r = 3`, `0.31 %` at `r = 5` |
| encoding costs more than solving | instance 40: encode `0.078 s`, solve `0.017 s` |
| proof checking dominates everything | instance 40: `2.78 s` — a property of my pure-Python checker, not of the reduction |
| the oracle already beats enumeration from `n = 18` | mean encode+solve vs mean enumeration: `n=16` `0.0195` vs `0.0193 s` (tie), `n=18` `0.0295` vs `0.0963 s` (**3.3×**), `n=20` `0.0526` vs `0.5682 s` (**10.8×**) |
| but proof checking costs more than both together | totals over 349: encode `8.4 s`, solve `3.4 s`, proof check `767.6 s` (`98 %`) |

So the answer to "do the distance constraints become the dominant cost" is **yes,
overwhelmingly** — over 99 % of the encoded formula, growing linearly in `|A|`, in
`n` and in the radius. That is the real scaling obstacle, and it is a property of
the cardinality encoding rather than of the SAT search, which stays cheap.

No extrapolated enumeration cost is reported anywhere as a measured speedup.

**On the new counting algorithm (motivation only).** `openai/math` `lean/docs/378.md`
states a deterministic machine that *exactly counts* satisfying assignments of a
canonically encoded `k`-CNF on `n` variables in time
`(L+1)^{O_k(1)} 2^{O_k(n(log log n)²/√(log n))}`, with `L` the encoding's bit length.
Two things follow, and neither is a dependency of this audit. First, it is a
**counting** result: it would supply the `|S_I|` denominator that §6 lacks, but it
does not decide `ε̂`, which an exact count does not determine. Second, any
complexity comparison must use the **encoded** size: `Q_r` for instance 40 is a
3-CNF on `5 344` variables, not on `16`. Substituting the original `n` into a
theorem about the enlarged formula would understate the variable count by a factor
of `334` on that instance alone. Nothing from 378 was implemented here.

## 8. Scope

This investigation targets resolution only. An exact `ε̂` does **not** determine
`|S_I|`, the number of connected components, the persistence or connectivity
structure, or whether `A` is a uniform sample, and none of those is claimed. Exact
counting and uniform sampling are recorded as possible later investigations and were
not begun. The paper's own separation of proved geometric facts, empirical findings
and open generalisations is preserved: nothing here upgrades an empirical finding,
and the `n ≤ 20` scope statement of its Discussion remains accurate for the
*phenomenon*, even though the *measurement* no longer needs enumeration.
